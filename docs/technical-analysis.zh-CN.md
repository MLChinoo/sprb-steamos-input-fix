# Summer Pockets REFLECTION BLUE 在 SteamOS 上的手柄兼容性崩溃：逆向分析与修复复盘

**项目：** Summer Pockets REFLECTION BLUE（Steam AppID：3418570）

**目标平台：** ASUS ROG Ally Z1 Extreme / Valve SteamOS

**分析工具：** IDA Pro、ida-pro-mcp、Codex、Python、SSH、Proton 日志

**修复方式：** 游戏可执行文件二进制补丁（Steam Input 图标数组边界检查）

**复盘日期：** 2026 年 11 月 22 日

## 一、事件概述

### 1.1 问题背景

在搭载官方 SteamOS 的 ASUS ROG Ally Z1 Extreme 上运行《Summer Pockets REFLECTION BLUE》时，游戏可以正常启动并进入主菜单，但尝试打开 **Settings（设置）** 或 **Load（读取存档）** 界面时，会立即发生崩溃。

该问题并非个例。ValveSoftware/Proton 仓库中的 [Issue #9948](https://github.com/ValveSoftware/Proton/issues/9948) 报告了几乎完全相同的现象。

原帖中值得注意的一点是：同一款游戏在相同硬件的 Bazzite 环境下可以正常运行，而在官方 SteamOS 下发生崩溃。

这说明问题可能并不来自 GPU 性能、游戏资源或基础图形兼容性，而是与两套系统对 Windows 游戏暴露的运行环境有关。

### 1.2 实际测试环境

| 项目         | 具体配置                    |
| ------------ | --------------------------- |
| 硬件         | ASUS ROG Ally Z1 Extreme    |
| 操作系统     | 官方 Valve SteamOS          |
| Linux Kernel | 7.2.7-valve2-2-neptune-72   |
| Proton       | 11.0-2e                     |
| InputPlumber | 0.78.0                      |
| 虚拟控制器   | deck-uhid                   |
| 虚拟设备名称 | Valve Steam Deck Controller |
| 游戏程序     | SummerPocketsRB.exe         |

通过 SSH 查询 InputPlumber，确认 SteamOS 将 ROG Ally 的实体控制器模拟为 Steam Deck 控制器。

### 1.3 前期排查结果

正式开展二进制逆向分析之前，已经完成以下兼容性测试：

| 测试项目                       | 结果 |
| ------------------------------ | ---- |
| 默认 Steam Input Gamepad 布局  | 崩溃 |
| 清除 Steam 控制器布局          | 崩溃 |
| Keyboard (WASD) and Mouse 布局 | 正常 |
| PROTON_PREFER_SDL=1            | 崩溃 |
| 完全禁用 Steam Input           | 崩溃 |

其中最关键的现象是：

**将 Steam Input 输出改为键盘鼠标后，Settings 和 Load 可以正常打开；使用手柄输入模式则会崩溃。**

因此，后续分析将重点放在 Steam Input 控制器识别、动作来源以及游戏内部手柄相关资源处理逻辑上。

## 二、从可分析 EXE 开始逆向调查

### 2.1 分析对象

原始游戏程序带有 SteamStub 保护，直接静态反汇编时，部分代码内容与实际运行时代码不一致。

通过解包处理，获得了可以在 IDA Pro 中进行静态分析的程序：

```
SummerPocketsRB.exe.unpacked.exe
```

Codex 使用 ida-pro-mcp 接入已经加载该文件的 IDA Pro 数据库。

IDA 识别到以下主要信息：

| 属性           | 结果        |
| -------------- | ----------- |
| 架构           | x86-64      |
| ImageBase      | 0x140000000 |
| ImageSize      | 0x235B000   |
| 函数数量       | 17,051      |
| 字符串数量     | 11,070      |
| .text 起始地址 | 0x140001000 |

解包后的 PE 文件包含 `.text`、`.idata`、`.rdata`、`.data`、`.pdata` 和 `.rodata` 等区域。

这使 Codex 能够直接通过崩溃日志中的地址定位函数，并进一步分析其调用关系。

### 2.2 从崩溃日志定位指令

Proton 日志中的核心异常为：

```
0xC0000005 — EXCEPTION_ACCESS_VIOLATION
```

异常位置：

```
SummerPocketsRB.exe + 0x1A6135
```

对应绝对地址：

```
0x1401A6135
```

IDA 反汇编确认该地址位于函数：

```
sub_1401A6120
```

关键机器指令如下：

```
0x1401A612D  mov rax, [rcx]
0x1401A6130  mov edi, edx
0x1401A6132  mov rbx, rcx
0x1401A6135  call qword ptr [rax+50h]
```

根据 Windows x64 调用约定，`RCX` 携带对象指针。

函数首先通过 `[RCX]` 读取对象的虚函数表指针，然后尝试调用虚函数表偏移 `0x50` 处的函数。

从 C++ 的角度，可以将其理解为：

```
object->VirtualMethod();
```

但崩溃时，寄存器中的虚函数表指针并不有效。

原始日志显示：

```
RAX = 0x0
```

因此，不能简单地把错误归结为某个 API 返回 NULL。需要继续查明被调用的对象究竟来自哪里。

## 三、追踪崩溃对象的来源

### 3.1 发现图像绘制调用链

继续分析 `sub_1401A6120` 的调用者，Codex 找到了：

```
sub_1402B7CB0
```

在该函数中，存在以下关键调用：

```
0x1402B8793  call sub_1400E5E60
```

以及：

```
0x1402B9524  call sub_1401A6120
```

结合上下文，可以确定：

- `sub_1400E5E60` 负责根据传入的标识查找游戏内部图像对象。
- `sub_1401A6120` 负责使用该对象执行后续图像处理或绘制。
- 调用者会使用查找结果，但并没有验证结果一定指向一个已正确构造的图像对象。

最初，崩溃看起来只是一次虚函数调用失败。

然而，调用链表明真正的问题可能发生得更早：**传入绘制函数的对象地址本身就不正确。**

### 3.2 确认图像对象类型为 cImage

在 IDA 中分析相关对象构造逻辑时，可以观察到：

```
sub_1401979A0
```

该函数负责初始化相关图像对象。

进一步检查全局初始化函数：

```
sub_1400158C0
```

发现其使用了 MSVC 编译器生成的数组构造逻辑：

```
eh vector constructor iterator(
    &unk_140F47360,
    0x20F8,
    0x196,
    sub_1401979A0,
    sub_140197A70
);
```

关键参数如下：

| 参数          | 含义           |
| ------------- | -------------- |
| unk_140F47360 | 图像数组基址   |
| 0x20F8        | 每个对象的大小 |
| 0x196         | 数组元素数量   |
| sub_1401979A0 | 对象构造函数   |
| sub_140197A70 | 对象析构函数   |

其中：

```
0x196 = 406
```

因此，可以确认游戏内部存在一组连续构造的 **406 个 cImage 对象**。

有效数组索引范围为：

```
0–405
```

每个对象大小为：

```
0x20F8 = 8,440 字节
```

数组查找逻辑使用的地址计算形式为：

```
object_address =
    array_base + index * 0x20F8
```

这里出现了重要的安全隐患：

只要 `index` 大于 405，计算出的地址就会落到已构造数组之外。

即使该地址仍位于进程可访问的内存区域，也不意味着其中存放着合法的 cImage 对象。

### 3.3 定位 Steam Input 动作来源

进一步分析 Steam Input 接口的调用关系后，Codex 确认游戏会查询控制器动作来源，并根据对应标识选择按钮图标。

相关逻辑集中在：

- `sub_1400E5500`：Steam Input 控制器状态、类型和相关数据处理。
- `sub_1400E5E60`：根据标识取得图标对象。
- `sub_1402B7CB0`：调用图标查找逻辑并继续处理。
- `sub_1401A6120`：对取得的图像对象执行虚函数调用。

这解释了为什么问题表现为打开 Settings 或 Load 时崩溃。

这些界面可能需要显示与手柄操作有关的按钮提示，因此会触发相应的图标获取和绘制流程。

问题实际上发生在 UI 资源处理阶段，而不是底层手柄输入完全无法工作。

## 四、根因确认：Steam Input 图标数组越界

### 4.1 出现超出数组范围的索引

结合崩溃日志、对象地址及数组布局，Codex 反算出导致崩溃的索引：

**413**

而游戏内部只有 406 个 cImage 对象。

对应关系如下：

| 项目                   | 数值 |
| ---------------------- | ---- |
| Steam Input 动作来源值 | 413  |
| 数组元素数量           | 406  |
| 最大合法索引           | 405  |
| 实际索引               | 413  |
| 判断结果               | 越界 |

也就是说，游戏试图访问：

```
cImage[413]
```

而实际上只能安全访问：

```
cImage[0]` 至 `cImage[405]
```

这一结果将最初看似随机的访问违规，定位为一个可以解释和修复的数组边界错误。

### 4.2 越界为什么会导致虚函数调用崩溃？

问题的关键在于，cImage 是具有虚函数表的 C++ 对象。

正常情况下：

```
cImage 对象
   |
   +-- vtable pointer
   |      |
   |      +-- virtual method
   |
   +-- 图像状态与纹理数据
```

当数组索引合法时，查找函数返回一个已构造的 cImage 对象。

但当索引为 413 时，程序计算出的地址已经越过数组边界。

该位置的内存并没有被保证初始化为合法的 cImage 对象。

于是，当绘制函数执行：

```
mov rax, [rcx]
call qword ptr [rax+50h]
```

它实际上把数组外的普通内存误认为 C++ 对象的虚函数表指针。

如果读到零，就会尝试访问接近空地址的内存。

如果读到其他无效值，同样可能发生访问违规。

因此：

**崩溃指令本身不是根因，错误发生在更早的图标对象查找阶段。**

### 4.3 为什么 SteamOS 更容易触发？

SteamOS 使用 InputPlumber，将 ROG Ally 的内置控制器模拟为 `deck-uhid`，即 Valve Steam Deck Controller。

Steam Input 会依据控制器类型和当前绑定关系返回动作来源标识。

Valve 在 Steamworks 文档中明确指出，`EInputActionOrigin` 会随着 Steam 客户端扩展；应用程序不应假定该枚举永远保持固定范围。

参考：

https://partner.steamgames.com/doc/api/ISteamInput#EInputActionOrigin

该游戏使用固定数量的图标对象来处理动作来源。

当 Steam Input 返回游戏未覆盖的新动作来源值时，如果直接用其进行数组索引，就会发生越界访问。

这也可以合理解释为什么：

- SteamOS 的 Steam Deck 虚拟控制器模式更容易触发问题。
- 键鼠布局能够规避相关按钮图标路径。
- 使用不同控制器管理方式的 Linux 发行版可能表现不同。

需要强调的是：**已确认的直接根因是数组越界；不同系统为什么返回不同的动作来源值，仍属于兼容性层面的解释，尚未完成跨系统逐项验证。**

## 五、最终修复方案设计

### 5.1 修复原则

既然已确定问题发生在图标查找阶段，就没有必要修改 SteamOS 的控制器驱动、InputPlumber 配置或者 Proton 的底层输入实现。

更合理的方式是：

**在游戏查找 cImage 对象之前验证索引范围，非法索引不再参与数组地址计算。**

整个修复应遵循：

- 不改变 Steam Input 的返回值。
- 不改变已存在的有效图标索引。
- 不改变原生手柄操作逻辑。
- 不修改游戏存档或图像资源文件。
- 越界时使用游戏已有的无图标处理路径。

### 5.2 补丁的核心逻辑

原始逻辑在概念上相当于：

```
cImage* GetGlyph(int origin)
{
    return &glyphs[origin];
}
```

这里假定 `origin` 一定处于预先构造的数组范围内。

修复后的逻辑相当于：

```
cImage* GetGlyph(int origin)
{
    constexpr int GLYPH_COUNT = 406;

    if (origin < 0 ||
        origin >= GLYPH_COUNT)
    {
        return nullptr;
    }

    return &glyphs[origin];
}
```

以上为根据最终修复行为整理的**等价伪代码**，不是实际补丁脚本的逐行内容。

核心变化是增加了索引有效性检查。

对于 `0–405`：

保持原有行为，使用正确的 cImage 对象。

对于 `413` 等非法索引：

不再计算数组外地址，而是走游戏原本已经存在的无图标处理分支。

### 5.3 为什么不需要修改绘制函数？

之前的崩溃虽然发生在：

```
0x1401A6135
```

但真正需要修复的位置是在其上游。

在绘制函数中添加简单的防御性判断，无法保证传入对象的有效性，因为数组外数据可能是任意非零值。

而在图标查找阶段检查范围，可以在错误地址形成之前就阻止越界访问。

因此，最终补丁选择修正图标对象查找，而不是修改最终发生访问违规的虚函数调用。

这既能覆盖已知越界情况，也减少了对正常绘制流程的影响。

## 六、具体二进制修复与部署

### 6.1 补丁脚本

Codex 编写了 Python 脚本：

```
patch_glyph_bounds.py
```

该脚本共 63 行，用于在解包后的 EXE 中应用图标索引边界检查。

补丁生成过程使用的本地源文件为：

```
SummerPocketsRB.exe.unpacked.exe
```

掌机端使用的源文件为：

```
SummerPocketsRB_unpacked.exe
```

补丁并非在所有调用图标的地方分别增加条件判断，而是采用**统一出口重定向（Shared Exit Redirection）**的方式，将多个图标查找分支共同使用的返回逻辑替换为带有边界检查的实现。

具体来说：

1. 找到图标查找函数内负责计算对象地址并返回的指令序列。
2. 将这些返回序列替换为跳转指令。
3. 把跳转目标统一指向一块尚未使用的可执行代码空间。
4. 在该空间内先检查索引是否小于 406。
5. 合法索引继续执行原有地址计算；非法索引返回 NULL。

这样可以避免在 16 个不同位置重复插入完整的边界检查代码。

### 6.2 定位原始返回逻辑

补丁的目标是图标查找函数：

```
sub_1400E5E60
```

脚本将搜索范围限制为：

| 参数         | RVA     |
| ------------ | ------- |
| LOOKUP_START | 0xE5E60 |
| LOOKUP_END   | 0xE61BE |

其中搜索区间为左闭右开，即：

```
[0xE5E60, 0xE61BE)
```

目标指令序列为：

```
imul rax, rax, 0x20F8
add  rax, rcx
ret
```

对应机器码：

```
48 69 C0 F8 20 00 00
48 03 C1
C3
```

合计 **11 字节**。

这段代码与之前通过 IDA 发现的数组结构完全吻合。

其中：

- `RAX`：图标数组索引。
- `RCX`：cImage 数组基地址。
- `0x20F8`：每个 cImage 对象的大小。
- `RET`：返回计算得到的对象地址。

执行后：

```
RAX = RCX + RAX * 0x20F8
```

问题在于，这段代码没有进行边界检查。

无论 `RAX` 是 5、100、405，还是非法的 413，都会直接计算并返回地址。

Codex 的补丁脚本最终在指定函数范围内找到 **16 处**完全相同的返回序列。

因此，修复必须覆盖全部 16 处出口，避免某些分支仍然能够绕过检查。

### 6.3 利用 Code Cave 保存新的检查逻辑

由于原始返回序列只有 11 字节，而完整的范围检查加地址计算需要更多空间，无法简单地在原位置插入所有指令。

为此，Codex 使用了常见的二进制修补技术：

**Code Cave（代码洞）注入。**

所谓 Code Cave，是指可执行文件中尚未被正常代码使用、可以容纳额外指令的空间。

本次选择的位置是：

```
RVA 0x6D6CAB
```

对应虚拟地址：

```
0x1406D6CAB
```

脚本将此位置定义为：

```
PADDING_RVA = 0x6D6CAB
```

在原始解包 EXE 中，该区域预期由 `0xCC` 字节填充。

`0xCC` 对应 x86 的 `INT3` 指令，通常可用于代码填充或调试断点。

为了避免覆盖已有指令，脚本会检查目标空间是否全部为预期的填充字节。

如果不符合预期，则直接拒绝修改。

这使补丁不会盲目写入未知的代码区域。

### 6.4 实际注入的机器码

在 Code Cave 中，脚本生成以下指令：

```
cmp eax, 0x196
jae invalid_index

imul rax, rax, 0x20F8
add  rax, rcx
ret

invalid_index:
xor eax, eax
ret
```

其中：

```
0x196 = 406
```

这段代码首先判断图标索引是否越界。

当索引合法时，继续执行原来的地址计算逻辑。

当索引非法时，直接将返回值置零。

对应完整机器码为：

```
3D 96 01 00 00
73 0B
48 69 C0 F8 20 00 00
48 03 C1
C3
31 C0
C3
```

总长度为 **21 字节**。

逐条解释如下：

| 机器码                 | 汇编指令                | 作用                        |
| ---------------------- | ----------------------- | --------------------------- |
| `3D 96 01 00 00`       | `cmp eax, 0x196`        | 与 406 比较                 |
| `73 0B`                | `jae +0x0B`             | 大于等于 406 时跳过地址计算 |
| `48 69 C0 F8 20 00 00` | `imul rax, rax, 0x20F8` | 计算对象偏移                |
| `48 03 C1`             | `add rax, rcx`          | 加上数组基地址              |
| `C3`                   | `ret`                   | 返回合法图像对象            |
| `31 C0`                | `xor eax, eax`          | 清零返回值                  |
| `C3`                   | `ret`                   | 返回 NULL                   |

这里最重要的指令是：

```
cmp eax, 0x196
jae invalid_index
```

`JAE` 表示无符号意义下的“大于或等于”。

因为比较使用的是 32 位 `EAX`，负索引在无符号比较中会被视为很大的整数。

因此，这一组指令能够同时排除：

- 负数索引。
- 大于等于 406 的索引。

最终只有 `0–405` 可以继续计算图像对象地址。

对于此次崩溃的索引 `413`：

```
413 >= 406
```

条件成立，程序跳转到：

```
xor eax, eax
ret
```

这样，非法索引不会再产生越界对象地址。

### 6.5 将 16 处返回序列统一重定向

新的检查代码已经写入 Code Cave，接下来需要让原来的图标查找出口执行它。

原始 11 字节：

```
48 69 C0 F8 20 00 00
48 03 C1
C3
```

被替换为：

```
E9 xx xx xx xx
CC CC CC CC CC CC
```

其中：

- `E9` 是无条件相对跳转 `JMP rel32`。
- 后面 4 字节保存有符号相对位移。
- 剩余 6 字节填充为 `0xCC`。

跳转目标统一为：

```
RVA 0x6D6CAB
```

相对位移的计算公式为：

```
displacement =
    PADDING_RVA - (tail_rva + 5)
```

其中 `tail_rva` 是当前被修改的返回序列位置。

由于 16 个出口的地址不同，所以每个出口 `E9` 后面的 4 字节位移也不同。

脚本会动态计算这些位移，而不是为所有位置写入相同的跳转字节。

整个过程可以表示为：

```
原始图标查找分支
         |
         v
原始地址计算出口
         |
         v
   JMP Code Cave
         |
         v
   cmp eax, 406
         |
    +----+----+
    |         |
  合法       非法
    |         |
    v         v
  imul       xor eax,eax
    |         |
    v         |
   add         |
    |         |
    v         v
   ret        ret
```

这样，无论游戏执行图标查找函数中的哪一个成功查找分支，最终都会经过统一的边界检查。

脚本还明确要求：

```
patched_exits == 16
```

如果实际找到的出口数量不是 16，就会抛出异常并停止生成补丁。

这可以防止游戏版本变化后，只修复部分分支而留下不可预测的行为。

### 6.6 RVA 与文件偏移的换算

本次补丁不是直接操作运行中进程的虚拟内存，而是对磁盘上的 PE 文件进行修改。

因此必须把 RVA 转换成文件偏移。

脚本使用：

```
TEXT_RVA    = 0x1000
TEXT_OFFSET = 0x400
```

转换公式为：

```
file_offset =
    TEXT_OFFSET + rva - TEXT_RVA
```

例如，Code Cave 的 RVA 为：

```
0x6D6CAB
```

对应文件偏移：

```
0x6D60AB
```

图标查找代码搜索范围对应的文件偏移为：

| 项目         | 文件偏移 |
| ------------ | -------- |
| LOOKUP_START | 0xE5260  |
| LOOKUP_END   | 0xE55BE  |
| Code Cave    | 0x6D60AB |

需要注意，这种换算方式建立在当前解包 EXE 的 `.text` 节布局上。

它不是适用于任意 PE 文件的通用公式，也不能直接用于未来版本。

### 6.7 SHA-256 与安全校验

补丁脚本使用严格的 SHA-256 校验，确保只能对经过确认的解包版本进行修改。

其要求的源文件 SHA-256 为：

```
4cac5967d6619f92190be84f3a25a255613c90ff95122296373cc9bf0ace8e64
```

脚本中的关键常量为：

```
BASE_SHA256 =
    "4cac5967d6619f92190be84f3a25a255613c90ff95122296373cc9bf0ace8e64"
```

这是**解包后 EXE** 的散列值，不是原始 SteamStub 保护文件的散列值。

补丁包含三项主要安全检查：

**第一项：文件版本检查**

如果输入文件的 SHA-256 不匹配，直接抛出异常：

```
Input does not match the supported unpacked build
```

**第二项：Code Cave 检查**

预定写入区域必须全部为 `0xCC`，否则拒绝修改：

```
Expected executable padding was not found
```

**第三项：出口数量检查**

必须找到恰好 16 处目标返回序列：

```
Expected 16 lookup exits, found ...
```

这可以保证补丁仅应用于经过确认的程序结构。

此外，输出文件使用 Python 的独占创建模式 `xb`。

如果输出路径已经存在，脚本会拒绝覆盖，有助于避免误覆盖现有文件。

## 八、问题的工程本质

这次问题体现了一个典型的第三方 API 兼容性错误：

**应用程序把外部 API 返回的枚举值当成了永远有效的内部数组索引。**

Steam Input 的动作来源枚举并不是一个可以永久假定大小不变的集合。

随着 Steam 客户端、控制器类型和输入设备支持范围扩展，API 可能返回游戏发布时未覆盖的新枚举值。

如果游戏采用固定大小的图标数组，却没有验证枚举范围，就可能出现：

1. 接收到新的动作来源标识。
2. 将标识直接转换为数组索引。
3. 访问超过预先构造范围的对象。
4. 将数组外数据误认为有效 C++ 对象。
5. 在调用虚函数时发生访问违规。

这种缺陷在普通测试环境中可能长期不出现，因为测试设备返回的枚举值始终位于合法范围内。

直到新设备或新的 Steam Input 行为触发更大的枚举值，问题才暴露出来。

从这一角度看，SteamOS 并不是唯一可能触发问题的平台。

只要有其他环境向游戏提供相同的越界动作来源值，理论上也可能发生类似崩溃。

## 九、后续维护及注意事项

### 9.1 游戏更新可能覆盖补丁

补丁是针对特定版本 EXE 生成的。

如果 Steam 更新游戏，可能发生：

- 原 EXE 被 Steam 替换。
- 函数地址发生变化。
- 图标数组大小变化。
- 代码空间布局变化。
- 补丁文件的预期字节不再匹配。

因此，不应在游戏更新后未经校验直接重新应用旧补丁。

建议在脚本中保留输入文件 SHA-256 检查，发现版本不一致时拒绝修改。

### 9.2 补丁不能自动补齐缺失图标

目前的修复目标是保证合法内存访问，不是扩展游戏的完整图标资源库。

如果动作来源 413 对应的图标没有游戏资源，边界检查会使其走无图标路径。

如果希望进一步完善视觉效果，可以研究将未知动作来源映射到通用 Xbox 或 Steam Deck 图标。

但这属于后续增强功能，不是本次崩溃修复所必需的部分。

### 9.3 应保留原版程序和补丁源码

建议长期保存：

- 原始 `SummerPocketsRB.exe`
- 解包后的分析版本
- `patch_glyph_bounds.py`
- 最终修复后的 EXE 的 SHA-256
- 原始与修复后的 Proton 日志
- 本次 IDA 分析结果

这样可以在游戏更新后重新定位查找函数，或将同一修复逻辑移植到其他版本。

### 9.4 建议向上游反馈

可以将这次发现的根因提交至：

https://github.com/ValveSoftware/Proton/issues/9948

建议反馈内容包括：

- 游戏内部 cImage 数组只有 406 项。
- Steam Input 返回了动作来源值 413。
- 游戏没有检查图标索引上界。
- 越界访问造成非法虚函数表调用。
- 增加边界检查后可规避该异常。
- 官方 SteamOS 的 `deck-uhid` 控制器模式无需修改。

这个问题的直接缺陷位于游戏的图标处理代码，因此从长期修复角度，也值得向游戏开发者反馈。

## 十、总结

本次问题最初表现为官方 SteamOS 上的手柄兼容性故障：

游戏能够正常启动，却会在打开 Settings 或 Load 时发生访问违规。

通过 Proton 日志、解包后的 PE 文件、IDA Pro 反汇编和调用链追踪，最终发现崩溃并不是简单的 Proton 图形兼容性问题。

**真正的根因是游戏内部 Steam Input 按钮图标查找逻辑缺少数组边界检查。**

游戏构造了一个包含 406 个 cImage 对象的数组，却在特定控制器环境下使用动作来源值 413 访问它，导致数组越界。

随后，游戏将越界内存误认为合法图像对象，在调用其虚函数时触发 `0xC0000005` 访问违规。

最终修复将判断逻辑前移至图标查找阶段：

**合法索引保持原有绘制行为；非法索引使用已有的无图标分支，避免生成错误的对象地址。**

具体实现采用了一种低侵入性的二进制补丁方式：将图标查找函数中 16 处原有的对象地址计算出口，统一重定向到 Code Cave，在那里执行无符号边界检查，随后根据结果返回合法对象地址或 NULL。

整个修复仅在游戏 EXE 内修改必要指令，不需要替换 Steam Input、Proton 或 InputPlumber，也不需要改变 SteamOS 的 `deck-uhid` 手柄模拟模式。

这一方案的价值不仅在于避免崩溃，还在于它不需要改变 SteamOS 的输入设备配置，不影响其他游戏，也无需放弃原生手柄操作。

本次排查也说明了一个重要的逆向分析原则：

**程序发生异常的位置不一定是真正产生错误的位置。沿数据来源向上追踪，往往比直接修改崩溃指令更有价值。**

通过定位数组的实际构造数量、对象大小以及上游输入来源，最终将一个看似复杂的 SteamOS/Proton 手柄兼容性问题，归结为一个明确的数组边界检查缺失问题。
